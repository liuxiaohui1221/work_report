一、微服务基础

1.1 什么是微服务？与单体架构的区别？

答案： 微服务是一种架构风格，将一个原本独立的系统拆分成多个小型服务，每个服务独立运行、独立部署，服务之间通过轻量级通信机制（HTTP/gRPC）进行协作。

维度 单体架构 微服务架构
部署方式 整体部署，一个应用包打天下 每个服务独立部署
技术栈 统一技术栈 服务可使用不同技术栈
扩展方式 整体扩展，资源浪费 按需扩展，资源利用率高
故障影响 一个模块故障，整体崩溃 故障隔离，不影响其他服务
开发效率 初期快，后期维护困难 初期架构成本高，后期维护简单
团队协作 依赖强，协作难 独立开发，协作灵活

面试加分话术：

"我参与的项目采用微服务架构，将系统按业务边界拆分为 api-server、platform、coordinator、metaserver、user-center 等多个服务，每个服务独立部署，通过 Nacos 实现服务注册与发现。"

【技术原理扩展】

微服务核心特征：

  1. 单一职责：每个服务聚焦一个业务能力，符合"高内聚低耦合"原则
  2. 独立进程：每个服务运行在独立进程中，通过进程间通信协作
  3. 去中心化：没有统一的技术栈，每个服务可根据业务特点选型
  4. API 通信：服务间通过明确定义的 API 通信，不依赖内部实现

Martin Fowler 微服务定义原文要点：

  • "围绕业务能力组织"（Organized around Business Capabilities）
  • Decentralized Data Management：每个服务可以有独立数据库
  • Infrastructure Automation：CI/CD 必须
  • Design for Failure：必须考虑故障

微服务 vs SOA 区别：

维度 SOA 微服务
ESB 有中心化 ESB 无 ESB，每个服务独立通信
服务粒度 粗粒度 细粒度
数据存储 共享数据库 独立数据库
技术栈 统一 去中心化

1.2 CAP 理论是什么？如何取舍？

答案： CAP 理论指出分布式系统最多同时满足两点：

  • C（Consistency）：所有节点数据一致
  • A（Availability）：每次请求都有响应
  • P（Partition Tolerance）：网络分区时系统仍可用

实际取舍：

  • CP 模式：强一致性场景（金融、支付）→ 牺牲可用性
  • AP 模式：高可用场景（社交、电商）→ 牺牲强一致性，追求最终一致

例如：Nacos 默认是 AP 模式，Eureka 是 AP 模式，Zookeeper 是 CP 模式。

【技术原理扩展】

CAP 三个理解误区：

  1. "三选二"不是"三选一"：分布式系统必须保证 P（分区容错），所以实际只能在 C 和 A 之间选择

  2. CAP 描述的是"同一个时刻"：不是"要么CP要么AP"，而是同一个操作在 CAP 之间取舍

  3. 一致性有强弱之分：

    • 强一致性（Linearizability）：任何时刻所有节点数据一致
    • 弱一致性：允许中间状态存在
    • 最终一致性：经过一段时间后达到一致

实战选型：

组件 CAP 原因
Zookeeper CP 分布式协调服务需要强一致，ZAB 协议保证
Eureka AP 服务发现允许短暂不一致，可用性优先
Nacos CP/AP 可切换 支持两种模式，通过配置选择
Redis Cluster AP 主从复制，最终一致，高可用

为什么 Eureka 是 AP？

  • 节点之间互相注册，每个节点都是对等的
  • 死亡节点不会被立即剔除，防止网络波动误判
  • AP 的体现：Eureka 优先保证可用性，即使部分节点不可用，服务发现仍可用

1.3 BASE 理论是什么？

答案： BASE 是 Basically Available（基本可用）、Soft state（软状态）和 Eventually consistent（最终一致性）三个短语的缩写。

BASE 理论的核心思想是：即使无法做到强一致性，但每个应用都可以根据自身业务特点，采用适当的方式来使系统达到最终一致性。

【技术原理扩展】

BASE 三要素详解：

  1. Basically Available（基本可用）：

    • 分布式系统出现故障时，允许损失部分可用性
    • 例如：双十一期间，淘宝降级为"商品展示可用，下单功能降级"
    • 核心思路：牺牲部分功能，保证核心功能

  2. Soft state（软状态）：

    • 允许系统中的数据存在中间状态，不强求强一致
    • 例如：订单状态可以是"支付中"，不是简单的"已支付/未支付"

  3. Eventually consistent（最终一致性）：

    • 系统在经过一段时间后，最终达到一致状态
    • "一段时间"取决于业务场景（秒级/分钟级/小时级）

BASE vs ACID：

特性 ACID（传统事务） BASE（微服务场景）
一致性 强一致 最终一致
可用性 低 高
适用场景 金融、订单 社交、电商、互联网

1.4 为什么选择微服务架构？

答案：

  • 分解业务逻辑，提高代码复用性和可维护性
  • 小规模业务独立成服务，提高系统扩展性
  • 支持分布式系统，适用于大规模和动态变化的应用场景
  • 便于团队独立开发、独立部署

注意避坑：

微服务不是银弹，团队规模小（3人以下）、日活低的项目不要强行拆分，运维成本会爆炸。

【技术原理扩展】

微服务适用条件（康威定律）：

  • 团队规模：建议 5-10 人的"two pizza team"，每个团队负责一个服务
  • 业务复杂度：业务边界清晰，可以独立拆分
  • 技术储备：需要 DevOps 能力（CI/CD、容器化、监控）
  • 流量规模：高并发场景，单体无法支撑

微服务不适用的场景：

  • 小型创业公司，团队 < 5 人
  • 低并发业务，日活 < 1000
  • 业务边界不清晰，模块耦合严重

【技术原理扩展】

为什么 Eureka 是 AP 而 Consul/Nacos 是 CP？

Eureka 遵循"自我保护"机制：

  • 节点之间互相注册，每个节点都是对等的
  • 死亡节点不会被立即剔除，防止网络波动误判
  • 最终一致性：可能出现短暂的服务列表不一致

Consul 使用 Raft 协议（CP）：

  • Leader 选举保证强一致性
  • 所有写操作必须经过 Leader
  • 网络分区时，少数节点不可用（牺牲可用性）

Nacos 双模式设计：

  • CP 模式（使用 Raft 协议）：用于配置管理，强一致性，Leader 选举，三节点保证高可用
  • AP 模式（使用 Distro 协议）：用于服务注册，最终一致性，任何节点可写入，数据异步同步

Distro 协议核心特点：

  • 分片机制：每个节点负责一部分服务实例
  • 同步策略：节点间异步同步数据
  • 写操作：写入当前节点，通过异步任务同步到其他节点
  • 读操作：直接读本地数据，延迟低

2.3 Nacos 1.x 作为注册中心的原理？

答案：

  1. 服务注册：服务启动时，通过 API 向 Nacos 注册自己的 IP 和端口
  2. 心跳机制：服务每 5 秒发送心跳，15 秒超时标记非健康，30 秒剔除
  3. 服务发现：消费者从 Nacos 拉取服务列表，本地缓存
  4. 配置推送：长轮询机制（默认 30s），配置变更时主动推送

底层实现：

  • Nacos 底层基于 Netty 实现
  • 集群数据同步使用 Distro 协议
  • 注册信息使用 ConcurrentHashMap 存储

【技术原理扩展】

服务注册流程详解：

1. 服务启动 → 读取配置 nacos.server-addr
2. 发送 REST API 注册到 Nacos Server
3. Nacos Server 存储到 ConcurrentHashMap（线程安全）
4. 同步到其他 Nacos 节点（Distro 协议）

心跳机制时间轴：

时间 状态
0s 服务注册，healthy = true
5s 第一次心跳
15s 第三次心跳过期，healthy = false
30s 实例被剔除（从注册表删除）

方式 Nacos 1.x Nacos 2.0+

延迟 1-3 秒 < 100ms

2.4 Nacos 是如何做到更新配置不重启微服务的？

答案：

  1. 长轮询机制：客户端发起轮询请求到服务端，当服务器端的配置没有变更时，连接会一直打开，直到超时或配置变更
  2. 两阶段优化：
    • 第一阶段：客户端把配置 key 的 MD5 发送到服务端比较
    • 第二阶段：客户端只获取变更的 key 对应的 value
  3. 减少网络通信：客户端把需要更新的配置进行分片，每个分片大小是 3000
  4. 动态刷新：通过 @RefreshScope 注解或 @ConfigurationProperties 实现配置 Bean 重建

【技术原理扩展】

Spring Cloud Config 动态刷新原理：

1. 启动时：微服务从 Nacos 拉取完整配置，存入本地内存和文件
2. 长轮询：客户端每 30s 发送请求，比较配置 MD5
   - MD5 不一致 → 返回变化的 key
   - MD5 一致 → 等待 30s 超时
3. 获取变更：客户端调用 Nacos API 获取最新值
4. 刷新 Bean：更新 @RefreshScope Bean 实例（新配置值）

@RefreshScope 原理：

  • refresh scope 每次使用时创建新的 Bean 实例
  • 配置变更时，清空 Bean 缓存
  • 下次使用时，重新创建 Bean 实例
  • 新实例自动注入最新配置值

MD5 比较优化：

  • 避免传输完整配置数据
  • 只传输变化的 key，减少网络带宽
  • 配置文件分片（每个分片最多 3000 个 key）

MD5 是如何计算的？

MD5 不是基于 key 本身生成的，而是基于 key+value 配对后的完整配置内容 生成的。

配置内容：
  jdbc.url = jdbc:mysql://localhost:3306/db
  jdbc.maxPoolSize = 20
  jdbc.timeout = 3000

MD5("jdbc.url=jdbc:mysql://localhost:3306/dbjdbc.maxPoolSize=20jdbc.timeout=3000")

启动时，客户端把每个配置 dataId 的完整内容拼成字符串，算出 MD5，发给服务端比较。两端 MD5 一致则配置未变，不一致则服务端返回变化 key 列表。

分片（3000 key）的实际含义：

分片不是为了"哪个分片在哪个服务器"，而是精准定位变更粒度的优化手段。

客户端本地有 10,000 个 key，按 3000 个一组分组：

Shard-1: key_0001 ~ key_3000    →  MD5_s1
Shard-2: key_3001 ~ key_6000    →  MD5_s2
Shard-3: key_6001 ~ key_9000    →  MD5_s3

长轮询请求体变成了每个分片 MD5 的集合，服务端逐分片比较后返回：

服务端返回：分片 1 和分片 3 的这些 key 变了
客户端只需请求变化分片中的那几个 key 的 value（不是整个文件）

这样即使改动 3 个 key，客户端也只需要拿这几个值，而不是全量拉取 10,000 个 key。

服务器新增 key 的处理：

服务端在原配置文件中新增一个 key → 内容变了 → MD5 不等 → 服务端告诉客户端"这个分片的这些 key 变了" → 客户端只拿新增的那几个 key 的 value 来更新。流程完全一样，无需重启。

2. Nacos 节点广播变更事件给所有订阅的客户端

影响 说明
Bean 重建 整个 Bean 重新实例化，依赖它的其他 Bean 也重建

状态丢失 Bean 中的实例变量（内存状态）会丢失

2.5 为什么 Feign 第一次调用耗时很长？

答案： Ribbon 默认是懒加载的，只有第一次调用的时候才会生成 Ribbon 对应的组件，这就会导致首次调用会很慢的问题。

解决方案：

ribbon:
  eager-load:
    enabled: true
    clients: service-1

【技术原理扩展】

Ribbon 懒加载机制：

首次调用时：
1. Interceptor 拦截请求
2. 首次初始化 ZoneAwareLoadBalancer
3. 从 Eureka/Nacos 拉取服务列表（网络请求）
4. 创建线程池、计算可用区
5. 执行负载均衡、发送 HTTP 请求

耗时：500ms - 2000ms（根据网络和服务数量）

Ribbon 组件初始化流程：

  • ZoneAvoidanceRule：负载均衡规则
  • ServerList：服务列表获取
  • IPing：健康检查
  • 所有操作在第一次同步执行，造成卡顿

OpenFeign 版本差异：

  • Feign 0.x（集成 Ribbon）：默认懒加载，首次调用慢
  • Feign 10.x + Spring Cloud 2020.x：使用 Spring Cloud LoadBalancer，改为服务注册后立即加载

2.6 Feign 的性能优化？

答案： Feign 底层默认是 JDK 自带的 HttpURLConnection，它是单线程发送 HTTP 请求的，不能配置线程池。使用 OkHttp 或 HttpClient 来发送 http 请求，它们都支持线程池。

feign:
  okhttp:
    enabled: true  # 使用 OkHttp
  httpclient:
    enabled: true  # 或者使用 HttpClient

【技术原理扩展】

HttpURLConnection 的性能问题：

  • 每次请求都创建新连接
  • 无连接池，TCP 三次握手开销大
  • 同步阻塞，线程资源浪费
  • 无法复用连接

OkHttp 连接池原理：

ConnectionPool pool = new ConnectionPool(
    maxIdleConnections: 5,    // 最大空闲连接数：同一主机最多保持 5 个空闲连接
    keepAliveDuration: 5,    // 空闲存活时间：连接空闲 5 分钟后被回收
    TimeUnit.MINUTES
);

// 工作原理：
// 1. 空闲连接保持在池中：连接用完不断开，放回池里等待复用
// 2. 相同主机的请求复用已有连接：发往 user-service 的请求复用同一个 TCP 连接
// 3. 自动回收过期连接：超过 5 分钟空闲的连接被后台线程清理
// 4. 支持 HTTP/2 多路复用：HTTP/2 下同一连接可并行发送多个请求

OkHttp vs Apache HttpClient 对比：

特性 OkHttp Apache HttpClient
连接池 内置 需手动配置
HTTP/2 支持 5.x 支持
Gzip 压缩 自动 需配置
线程安全 完全安全 需池化

2.7 Nacos 集群节点数据同步？

答案：

  • 每个节点都维护了全量的数据
  • 节点之间数据同步基于 Distro 协议来完成
  • Distro 协议特点：每个节点自己负责部分的写请求，每个节点会把自己负责的新增数据同步给其他节点

【技术原理扩展】

Distro 协议数据同步流程：

场景：客户端在 Node-1 注册 order-service（假设 order 在 N-T 范围，应由 Node-2 负责）

1. Node-1 收到注册请求，检查发现 order 不在自己负责的 A-M 范围
2. Node-1 临时存储在自己的注册表中（用于处理"路由期间"的请求）
3. 异步同步任务启动：将 order-service 信息同步给 Node-2
4. Node-2 确认收到，存储到自己的注册表
5. Node-1 删除临时数据（已同步完成）
6. 后续 order-service 的读请求直接由 Node-2 提供

  • Nacos 2.0+ 使用 gRPC 长连接（端口 9848）
  • 服务端主动推送（服务变更、配置变更）
  • 心跳复用已有连接（复用 TCP）
  • 双向通信（服务端可主动推送）

@Component
@Slf4j
public class JwtAuthGlobalFilter implements GlobalFilter, Ordered {

    @Autowired
    private JwtUtil jwtUtil;

    // 过滤器的优先级，数字越小越先执行
    @Override
    public int getOrder() {
        return -100; // 在大部分内置过滤器之前执行
    }

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // 1. 公开路径放行（登录、注册、文档）
        if (path.startsWith("/api/user/login") ||
            path.startsWith("/api/user/register") ||
            path.startsWith("/swagger")) {
            return chain.filter(exchange);
        }

        // 2. 从 Header 中取 Token
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");

        // 3. 校验 Token
        if (StringUtils.isBlank(token) || !token.startsWith("Bearer ")) {
            log.warn("未授权请求: {} {}", exchange.getRequest().getMethod(), path);
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            // 返回 JSON 错误响应，而不是跳转到 /fallback
            exchange.getResponse().getHeaders().setContentType(MediaType.APPLICATION_JSON);
            String body = "{\"code\":401,\"msg\":\"请先登录\"}";
            return exchange.getResponse().writeWith(
                Mono.just(exchange.getResponse().bufferFactory().wrap(body.getBytes()))
            );
        }

        // 4. 解析 Token，验证通过后注入用户信息
        try {
            String realToken = token.substring(7); // 去掉 "Bearer " 前缀
            Claims claims = jwtUtil.parseToken(realToken);
            String userId = claims.getSubject();
            // 将用户 ID 注入到请求属性，后续业务代码可以直接读取
            exchange.getAttributes().put("userId", userId);
            log.debug("JWT 鉴权通过: userId={}, path={}", userId, path);
        } catch (JwtException e) {
            log.warn("Token 无效: {}", e.getMessage());
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().writeWith(
                Mono.just(exchange.getResponse().bufferFactory()
                    .wrap("{\"code\":401,\"msg\":\"Token 失效，请重新登录\"}".getBytes()))
            );
        }

        // 5. 继续过滤器链
        return chain.filter(exchange);
    }
}

Step 3：自定义 PredicateFactory（按时间灰度发布）

// 需求：只在白天 9:00-18:00 将请求路由到新版本
@Component
public class BetweenDayTimeRoutePredicateFactory
        extends AbstractRoutePredicateFactory<BetweenDayTimeConfig> {

    public BetweenDayTimeRoutePredicateFactory() {
        super(BetweenDayTimeConfig.class);
    }

    @Override
    public Predicate<ServerWebExchange> apply(BetweenDayTimeConfig config) {
        return exchange -> {
            ZonedDateTime now = ZonedDateTime.now(ZoneId.systemDefault());
            LocalTime current = now.toLocalTime();
            LocalTime start = config.getStart(); // 例如 09:00
            LocalTime end = config.getEnd();     // 例如 18:00
            return !current.isBefore(start) && current.isBefore(end);
        };

Netty 是 Gateway（和 WebFlux）的底层网络框架，它解决了传统 NIO 的两大痛点：

1. 传统 NIO 的问题—— Selector 轮询的"忙轮询"：

// 伪代码，传统 NIO
while (true) {
    selector.select();  // 阻塞等事件，但没有具体通知是哪个 Channel
    Set<SelectionKey> keys = selector.selectedKeys();
    for (SelectionKey key : keys) {

                                        这条连接的所有事件

【技术原理扩展】从 select → poll → epoll：I/O 多路复用的演进内幕

一、先理解为什么需要 I/O 多路复用

问题： 一个线程要同时处理成百上千个网络连接，最朴素的做法是什么？

朴素做法（阻塞 I/O）：
  线程 1 → accept() 等待客户端连接    → 等待中，啥也干不了
  线程 2 → read(socket1) 读数据        → 等待中，啥也干不了
  线程 3 → read(socket2) 读数据        → 等待中，啥也干不了
  ...
  1000 个连接 = 1000 个线程 = 线程切换开销巨大，内存爆炸

I/O 多路复用的核心思想： 用一个（或少量）线程，同时管理多个文件描述符（socket），哪个就绪了就去处理哪个。

二、第一代：select() 的缺陷（1983 年 BSD 实现）

// select 伪代码
int select(int nfds,              // 要监控的最大 fd + 1（遍历上界）
           fd_set *readfds,       // 读事件关注列表
           fd_set *writefds,      // 写事件关注列表
           fd_set *exceptfds,     // 异常事件关注列表
           struct timeval *timeout);  // 超时

select 的三大致命问题：

问题 1：fd 数量上限（默认 1024）

// Linux 内核中 fd_set 的实现是一个固定长度的位图
#define __FD_SETSIZE  1024   // 硬编码，只能监控 1024 个 fd

typedef struct {
    unsigned long fds_bits[__FD_SETSIZE / sizeof(long)];
} fd_set;

// 这意味着 select 无法用于需要监控数万连接的场景（如网关）

问题 2：用户态→内核态拷贝开销（每次调用都要拷贝）

每次调用 select():
  用户态                          内核态
  ┌──────────┐  ──拷贝 fds_bits──▶  ┌──────────────┐
  │ 应用进程 │   （readfds 整个复制）│  监听所有 fd │
  └──────────┘                      └──────────────┘

假设有 10 万连接，每次 select() 调用都要把这 10 万个 fd 全部复制到内核
——即使 99% 的连接从来不活跃，这 99% 的拷贝也是白做的

问题 3：内核遍历返回后，应用层仍需 O(n) 遍历所有 fd

// select 返回"有事件发生"，但没告诉你具体是哪个
// 必须遍历全部 nfds 逐一检查
FD_ZERO(&result);
select(nfds, &readfds, NULL, NULL, NULL);

// 这里必须遍历全部 1024 个 fd 才能找到就绪的那个
for (int i = 0; i < nfds; i++) {
    if (FD_ISSET(i, &readfds)) {
        // 只有这里才是真正需要处理的
        handle(i);
    }
}

时间复杂度： 每次调用都是 O(n)，n = 全部监控的 fd 数量，不是就绪的 fd 数量。

三、第二代：poll() 的改进

// poll 伪代码（解决了 fd 数量上限问题，但没解决拷贝开销）
struct pollfd {
    int   fd;       // 要监控的文件描述符
    short events;   // 关注的事件（POLLIN / POLLOUT）
    short revents;  // 返回时：实际发生的事件
};

int poll(struct pollfd *fds, nfds_t nfds, int timeout);

poll 相比 select 的改进：

select poll
fd 数量上限 1024（硬编码） 无上限（动态数组）
传参方式 三个固定位图（read/write/error） 动态数组，结构更清晰
用户→内核拷贝 整数组拷贝（每次都拷贝全部） 整数组拷贝（同样每次都拷贝全部）

poll 的核心问题：仍然是每次调用都要把整个数组从用户态拷贝到内核态。 即使用动态数组解决了 1024 上限，但拷贝开销没有本质改善。

四、第三代：epoll（Linux 2.6+）—— 真正解决问题

epoll 提出了一个关键洞察：能不能不要每次调用都重复拷贝？能不能只告诉我在哪里发生了事件？

epoll 由三个系统调用组成：

// 1. 创建 epoll 实例（在内核中创建一个"监控管理结构"）
int epoll_create(int size);  // size 提示内核初始化多大（2.6 后忽略但需 > 0）
// 返回一个 epoll 文件描述符 epfd

// 2. 注册要监控的 fd 及事件类型
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
// op: EPOLL_CTL_ADD（新增）/ EPOLL_CTL_MOD（修改）/ EPOLL_CTL_DEL（删除）
// event: 要监听的事件类型（EPOLLIN / EPOLLOUT / EPOLLET 等）

// 3. 等待事件发生（核心调用）
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
// 返回就绪的事件列表（直接是可用的，不需要遍历）

epoll 的三大核心改进：

改进 1：内核态维护监控列表，只拷贝增量变更

select/poll 模式（每次调用都拷贝全部）：
  用户态 ──拷贝 10 万个 fd──▶ 内核态（每次！）

epoll 模式（只在增删时拷贝）：
  创建时：epoll_create() ──▶ 内核分配监控结构
  注册时：epoll_ctl(ADD fd) ──▶ 只拷贝 1 个 fd + 1 个 event
  等待时：epoll_wait() ────────▶ 不拷贝！直接返回就绪列表

关键：epoll_wait() 只返回就绪的事件，不需要传入全部 fd 列表。 监控列表在内核中维护，增删改时才触发一次拷贝。

改进 2：返回就绪列表而非全量遍历

// select/poll：返回"有事件"，你需要自己遍历全部 fd 找出来
for (int i = 0; i < 100000; i++) {
    if (FD_ISSET(i, &readfds)) { ... }  // O(n) 遍历
}

// epoll_wait：直接返回就绪的 fd 列表
struct epoll_event events[1024];
int n = epoll_wait(epfd, events, 1024, -1);  // n = 就绪数量，通常很小

// 只需遍历这 n 个就绪的 fd，n << total fd
for (int i = 0; i < n; i++) {
    handle(events[i].data.fd);  // O(就绪数量)
}

改进 3：两种触发模式——边缘触发（ET）vs 水平触发（LT）

这是 epoll 最重要的特性，也是最容易踩坑的点：

水平触发（Level Triggered, LT）：（select/poll 默认模式）

状态：socket 缓冲区一直有数据
LT 行为：每次 epoll_wait 都返回"可读"，直到缓冲区被读完
类比：电平信号，只要是高就持续通知
特点：编程友好，不会漏事件，但会重复通知

边缘触发（Edge Triggered, ET）：（Netty 采用）

状态：socket 缓冲区从"空"变成"有数据"（一次跳变）
ET 行为：只在数据首次到达时通知一次，之后不再通知，直到下次新数据到来
类比：脉冲信号，只在上升沿/下降沿通知一次
特点：效率更高（只通知一次），但要求必须一次性读完，否则事件会丢失

ET 边缘触发时序示例：

时刻1：客户端发送数据 → 缓冲区从空变为有数据
  epoll_wait 返回：fd 可读 ✅（一次通知）
时刻2：应用层还没来得及 read()，又来了一批数据
  epoll_wait 不返回（缓冲区一直有数据，没有新的跳变）
时刻3：应用 read() 读完所有数据，缓冲区变空
时刻4：再下一批数据到来时
  epoll_wait 返回：fd 可读 ✅（又一次跳变通知）

为什么 Netty 用 ET（边缘触发）？

// Netty 的 ByteBuf 读取必须在 ET 模式下一次性读完
// 如果没读完，epoll 不会再次通知，连接就"卡死"了
// 所以 Netty 内部有一个 ReadPending 机制来保证读完

// ET 模式要求：
// 1. 使用非阻塞模式（O_NONBLOCK）
// 2. 一次性把缓冲区读完（循环 read 直到 EAGAIN）
// 3. 否则会丢事件（这是 bug 的主要来源）

五、三种机制完整对比

维度 select poll epoll
fd 数量上限 1024（硬编码位图） 无上限（动态数组） 无上限（红黑树）
监控列表维护 每次调用拷贝全部 每次调用拷贝全部 内核常驻，增删时单条拷贝
返回结果 只返回"有/无"，需 O(n) 遍历 同 select 直接返回就绪列表 O(k)，k=就绪数
时间复杂度 O(n)，n=全部 fd O(n) O(k)，k=就绪 fd
触发模式 水平触发 水平触发 水平触发 + 边缘触发
跨平台 POSIX 标准，全平台 POSIX 标准 仅 Linux（Mac 用 kqueue）
10 万连接活跃 10 个的场景 每次调用拷贝 10 万 每次调用拷贝 10 万 注册时拷贝 10 个，之后每次只返回 10 个

六、epoll 底层数据结构——红黑树 + 就绪链表

内核中每个 epoll 实例维护两个核心结构：

┌─────────────────────────────────────────────────────────┐
│                    epoll 实例（epfd）                   │
│                                                         │
│   ┌───────────────────┐      ┌──────────────────────┐  │
│   │  红黑树（监控列表） │      │   就绪链表（就绪事件） │  │
│   │  RB-Tree          │      │   ready_list        │  │
│   │                   │      │                      │  │
│   │  O(log N) 增删改   │      │  O(1) 插入（就绪时）  │  │
│   │  存储所有被监控    │      │  epoll_wait 直接返回  │  │
│   │  的 fd 和事件      │      │  整个链表内容        │  │
│   │                   │      │                      │  │
│   │  epoll_ctl 操作   │      │  socket 变为可读时    │  │
│   │  的目标结构        │      │  内核自动加入链表     │  │
│   └───────────────────┘      └──────────────────────┘  │
│                                                         │
│   ┌─────────────────────────────────────────────────┐  │
│   │           双向链表条目（epitem）                  │  │
│   │  每个被监控的 fd 对应一个 epitem，                │  │
│   │  同时存在于红黑树和就绪链表中                     │  │
│   └─────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘

为什么用红黑树而不是哈希表？
→ 红黑树 O(log N) 查找/删除，在 10 万连接量级和哈希 O(1) 差距可忽略
→ 但红黑树有序，epoll_ctl(ADD/MOD/DEL) 操作更稳定
→ 哈希表在大量增删时可能有扩容 rehash 抖动

七、Netty 中的 epoll 应用

// Netty 自动选择最优 Selector 实现
// Linux：EpollEventLoopGroup → 使用 epoll（边缘触发）
// Mac：KQueueEventLoopGroup → 使用 kqueue（类似 epoll 的 BSD 实现）
// Windows：NioEventLoopGroup → 回退到 select（Windows 原生不支持 epoll）

// 生产环境推荐用 Epoll（Linux）
EventLoopGroup bossGroup = new EpollEventLoopGroup(1);  // 处理连接
EventLoopGroup workerGroup = new EpollEventLoopGroup();  // 处理 I/O，CPU 核数 × 2

ServerBootstrap sb = new ServerBootstrap();
sb.group(bossGroup, workerGroup)
  .channel(EpollServerSocketChannel.class)  // 使用 Epoll 类型的 Channel
  ...

Netty 为什么要自己封装 epoll，而不直接用 JDK NIO？

JDK NIO 的 Selector（Linux）：
  → 使用水平触发（LT）模式，不支持边缘触发（ET）
  → 每次 select() 返回后，JDK 内部还要再遍历一遍
  → JDK 内部有锁（SelectionKey 集合的并发控制）

Netty 的 EpollSelectorProvider：
  → 使用边缘触发（ET）模式，真正高效
  → 无锁化（每个 EventLoop 独享自己的 Selector）
  → 直接调用 Linux epoll_xxx 系统调用，跳过 JDK 层
  → epoll 水平触发模式下，JDK 会重复通知，导致空轮询 bug（Selector 空转 100% CPU）

JDK NIO epoll 空轮询 bug： JDK 在 Linux 下使用 epoll 水平触发，但实现有缺陷——某些情况下即使没有事件也会返回（假唤醒），导致 Selector.select() 立即返回空结果，不断空转消耗 CPU。Netty 通过 EpollSelectorProvider 直接操作 epoll，绕过了这个 bug。

八、完整流程对比：1 万连接 10 个活跃的场景

场景：1 万个连接，其中 10 个有数据到达

select():
  每次调用：拷贝 1 万个 fd 到内核 → 返回"有" → 遍历 1 万个找 10 个
  → 10 万次遍历 + 每次 1 万拷贝

poll():
  每次调用：拷贝 1 万个 pollfd 到内核 → 返回"有" → 遍历 1 万个找 10 个
  → 10 万次遍历 + 每次 1 万拷贝（和 select 本质一样）

epoll():
  创建时：epoll_create → 内核分配红黑树 + 就绪链表
  注册 1 万个：epoll_ctl(ADD) × 1 万 → 每次拷贝 1 个 fd = 1 万次单条拷贝
  等待时：epoll_wait → 只返回 10 个就绪的 fd
  → 0 次全量拷贝 + 每次最多 10 次处理

结论： 连接数越多、活跃比例越低，epoll 优势越明显。这也是为什么 Spring Cloud Gateway 能达到 50k-100k QPS 的根本原因——它用 epoll（Linux）+ WebFlux 异步非阻塞，用极少线程（几个 EventLoop）处理海量连接。

Spring Gateway HandlerMapping（路由匹配，找到 Route）
    │
    ▼

【技术原理扩展】WebFlux / Flux / Mono 核心方法详解

背景：为什么需要响应式编程

传统同步阻塞模型的瓶颈： 一个线程处理一个请求，I/O 等待时白白阻塞。100 个并发进来就需要 100 个线程。

回调式异步的困境——回调地狱：

// 嵌套不断加深，逻辑分散，异常处理各自独立，无法链式组合
getUserName(id, new Callback() {
    @Override
    public void onResult(User user) {
        getOrders(user.getId(), new Callback() {
            @Override
            public void onResult(List<Order> orders) {
                getProducts(orders, new Callback() {
                    // 三层嵌套，完全无法维护
                });
            }
        });
    }
});

Flux/Mono 的解决思路： 把"值什么时候来"变成一个可以传递的对象。方法返回的不再是直接结果，而是"异步承诺"，调用方通过 .map() / .flatMap() 链式组合多个异步操作，无需嵌套回调。

// 返回的是 Mono<String>（异步承诺），不是 String
public Mono<String> getUserName(Long userId) {
    return userRepository.findById(userId)  // Mono<User>
        .map(user -> user.getName());         // 转成 Mono<String>
}

调用方拿到 Mono<String> 后，可以用 .map() / .flatMap() 链式组合多个异步操作，没有回调嵌套。

一、Flux vs Mono 的区别（均来自 Reactor 库）

Flux：异步发出 0 到 N 个元素的数据流，类比异步版的 Stream<T>，适合查询列表、消息流等场景。

Mono：异步发出最多 1 个元素，类比 Optional<T> 的异步版，适合 HTTP 单次响应、查单个记录。

相互转换：

Flux<User> flux = userRepository.findAll();

// 取第一个 → Mono
Mono<User> first = flux.next();

// 计数 → Mono
Mono<Long> count = flux.count();

// 收集成列表 → Mono
Mono<List<User>> list = flux.collectList();

二、核心方法分类

第一类：创建（Creating）

1. just() —— 直接创建

// Mono：创建包含单个值的发布者（立即发射一个值）
Mono<String> mono = Mono.just("hello");

// Flux：创建包含多个值的发布者（按顺序发射每个值）
Flux<String> flux = Flux.just("apple", "banana", "cherry");

// empty()：创建空流（不发射任何值，直接完成）
Mono<String> emptyMono = Mono.empty();

// error()：创建错误流（订阅时直接抛出异常）
Mono<String> errorMono = Mono.error(new RuntimeException("出错啦"));

2. fromIterable() —— 从集合创建

// 将 List 转为 Flux，按顺序发射每个元素
List<User> users = List.of(user1, user2, user3);
Flux<User> flux = Flux.fromIterable(users);
// 订阅后依次收到 user1, user2, user3

3. generate() —— 同步逐个生成（有限流）： 由订阅者"拉取"驱动，每次请求产生一个元素，同步执行，常用于分页等场景。

4. create() —— 异步批量生成（Gateway 常用）： 由生产者"推送"驱动，通过 FluxSink 手动控制何时发值、何时结束，适合把老系统的回调 API 适配成响应式流。

传统回调写法（你没法改的老系统）：

// 老的消息监听器，只能用回调注册
listener.addCallback(new MessageCallback() {
    @Override
    public void onMessage(String msg) {
        System.out.println("收到: " + msg);
    }
    @Override
    public void onError(Exception e) {
        System.err.println("出错: " + e);
    }
    @Override
    public void onClose() {
        System.out.println("结束");
    }
});

三个独立回调，各自处理各自的事件，互不相关，无法链式操作。

用 Flux.create() 包装：

public Flux<String> toFlux(OldListener listener) {
    return Flux.create((FluxSink<String> sink) -> {
        // onDispose：取消订阅时的清理回调
        // 作用：防止内存泄漏，订阅取消时主动断开监听器连接
        sink.onDispose(() -> {
            System.out.println("订阅取消，清理监听器");
        });

        // 注册老系统的回调，转换为 Flux 的事件流
        listener.addCallback(new MessageCallback() {
            @Override
            public void onMessage(String msg) {
                // next()：把消息发入 Flux 流，订阅者就能收到这条消息
                sink.next(msg);
            }
            @Override
            public void onError(Exception e) {
                // error()：把错误发入 Flux 流，触发订阅者的 onError 处理
                sink.error(e);
            }
            @Override
            public void onClose() {
                // complete()：流正常结束，触发订阅者的 onComplete 回调
                sink.complete();
            }
        });
    });
}

包装后就可以链式处理：

toFlux(listener)
    .filter(msg -> !msg.contains("广告"))          // 过滤广告
    .take(5)                                       // 只取前5条
    .map(msg -> "【收到】" + msg)                  // 加工消息
    .timeout(Duration.ofSeconds(10))               // 10秒无消息算超时
    .onErrorResume(e -> Flux.just("降级消息"))     // 出错降级
    .subscribe(
        msg -> System.out.println(msg),            // 处理消息
        err -> System.err.println("错误: " + err), // 错误处理
        () -> System.out.println("--- 接收完毕 ---") // 完成处理
    );

Flux.create() 改造后的好处：

能力 回调写法 Flux.create() 包装后
链式操作 ❌ 无法链 ✅ filter/map/flatMap 随便链
统一错误处理 ❌ 每处单独 try-catch ✅ 一处 .onErrorResume()
背压控制 ❌ 无，来多少收多少 ✅ .onBackpressureBuffer()/Drop()
多源合并 ❌ 各自处理 ✅ .merge() / .zip()
逻辑复用 ❌ 和数据源耦合 ✅ .transform() 抽离
接 WebFlux ❌ 无法直接转 SSE ✅ 直接返回 Flux<T> 给 Controller
资源清理 ❌ 手动写 ✅ sink.onDispose() 自动清理

统一错误处理示例：

// 回调写法：每个地方都要单独 try-catch
listener.addCallback(msg -> {
    try { process(msg); } catch (Exception e) { logger.error(e); }
});

// Flux 写法：一处搞定
toFlux(listener)
    .map(this::process)
    .onErrorResume(e -> {
        logger.error("处理失败", e);
        return Flux.empty();  // 出错了返回空流，不影响其他逻辑
    })
    .subscribe();

背压控制示例：

toFlux(listener)
    .onBackpressureBuffer(100)         // 缓冲区最多存100条
    .onBackpressureDrop(msg -> log.warn("消息积压，丢弃: " + msg))  // 满了丢弃慢的
    .publishOn(Schedulers.boundedElastic())  // 限速消费
    .subscribe(msg -> handleExpensive(msg));

多源合并示例：

// 两个流合并，统一处理
Flux<String> chatFlux = toFlux(chatListener);
Flux<String> systemFlux = toFlux(systemListener);

Flux.merge(chatFlux, systemFlux)
    .filter(msg -> !msg.isBlank())
    .take(10)
    .subscribe(msg -> handle(msg));

接 SSE 直接推给前端：

@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> stream() {
    return toFlux(listener)
        .filter(msg -> !msg.contains("广告"))
        .take(10)
        .map(msg -> "data: " + msg + "\n\n");  // 转成 SSE 格式
}

第二类：转换（Transforming）

1. map() —— 同步转换（一对一）

// map：对每个元素执行同步转换，返回值直接作为下一个元素
Flux.just(user1, user2, user3)
    .map(user -> user.getName())  // User → String，转换后类型 Flux<String>
    .subscribe(System.out::println);  // 依次打印每个用户的名字

2. flatMap() —— 异步转换（一对多，最核心也最易混淆）

// flatMap：当前元素触发新的异步操作，返回另一个 Flux/Mono
// 关键：自动把多个结果"扁平化"（flatten）合并成一整条流
// 注意：flatMap 不保证顺序（并发执行），flatMapSequential 保证顺序

// 场景：每个用户异步查询其订单
Flux.just(user1, user2, user3)
    .flatMap(user -> orderService.findByUserId(user.getId()))
    // orderService 返回 Mono<List<Order>>
    // flatMap 自动把 List<Order> 拆开，合并成 Flux<Order>
    .subscribe(order -> System.out.println(order));

// 对比：不用 flatMap 会变成嵌套 Mono（❌ 错误写法）
Flux.just(user1, user2, user3)
    .map(user -> orderService.findByUserId(user.getId()))
    // 结果是 Flux<Mono<List<Order>>>，嵌套了两层，无法正常处理

3. filter() —— 过滤

// filter：根据条件过滤元素，保留满足条件的元素
Flux.range(1, 10)  // 依次产生 1, 2, 3, ..., 10
    .filter(n -> n % 2 == 0)  // 过滤保留偶数
    .subscribe(System.out::println);  // 输出：2, 4, 6, 8, 10

4. take() / skip() —— 取前N个 / 跳过前N个

// skip(3)：跳过前3个元素；take(4)：只取前4个元素
// 两个结合实现分页效果
Flux.range(1, 10)
    .skip(3)   // 跳过 1, 2, 3
    .take(4)   // 取接下来的 4 个：4, 5, 6, 7
    .subscribe(System.out::println);

5. reduce() / scan() —— 聚合

// reduce：所有元素汇总成单个结果（最终汇总值）
Flux.range(1, 5)
    .reduce((a, b) -> a + b)  // 累加：1+2+3+4+5
    .subscribe(System.out::println);  // 输出：15

// scan：逐步展示每一步的聚合结果（累加过程的每一步）
Flux.range(1, 5)
    .scan((a, b) -> a + b)
    .subscribe(System.out::println);  // 输出：1, 3, 6, 10, 15

6. zip() —— 合并多个流（按序号配对）

// zip：按位置一一配对，两个流相同索引的元素组合成元组
Flux<String> names = Flux.just("Alice", "Bob");
Flux<Integer> ages = Flux.just(25, 30);

Flux.zip(names, ages, (name, age) -> name + " is " + age)
    .subscribe(System.out::println);
// 输出：Alice is 25
//        Bob is 30

第三类：组合（Combining）

1. merge() / concat() —— 合并

Flux<String> f1 = Flux.just("A", "B");
Flux<String> f2 = Flux.just("1", "2");

// merge：时间序合并（谁先到谁先出，不保证顺序）
Flux.merge(f1, f2).subscribe(System.out::println);

// concat：严格按顺序，f1 全部发完再发 f2
Flux.concat(f1, f2).subscribe(System.out::println);  // A, B, 1, 2

2. startWith() / endWith() —— 头尾追加

Flux.just("B", "C")
    .startWith("A")
    .endWith("D")
    .subscribe(System.out::println);  // A, B, C, D

第四类：错误处理（Error Handling）——异步编程最重要的一部分

1. onErrorReturn() —— 出错返回默认值

// onErrorReturn：当流中出现错误时，替换为指定的默认值
userRepository.findById(1L)
    .onErrorReturn("Guest")  // 查询失败时，返回字符串 "Guest" 作为降级值
    .subscribe(System.out::println);

2. onErrorResume() —— 出错执行另一个 Flux/Mono

// onErrorResume：根据错误类型选择不同的降级策略
userRepository.findById(1L)
    .onErrorResume(e -> {
        if (e instanceof DataAccessException) {
            // 数据库异常：从缓存服务获取降级数据
            return fallbackService.getDefaultUser();
        }
        // 其他异常：重新抛出（不降级）
        return Mono.error(e);
    })
    .subscribe(System.out::println);

3. retry() —— 重试

// retry(n)：发生错误时自动重试最多 n 次
webClient.get().uri("/api/user/{id}", id)
    .retrieve().bodyToMono(User.class)
    .retry(3)  // 失败后最多重试 3 次（总共 4 次请求）
    .subscribe(System.out::println);

退避重试（间隔递增）：

// retryWhen：自定义重试策略，这里是指数退避
.retryWhen(Retry.backoff(3, Duration.ofSeconds(1)))
// 第 1 次重试：等待 1 秒
// 第 2 次重试：等待 2 秒（指数增长）
// 第 3 次重试：等待 4 秒

4. checkpoint() —— 调试友好（标记错误来源）

// checkpoint：在链式调用中添加"检查点"名称
// 出错时，错误信息会显示这个名称，而不是一长串堆栈
.orderService.findByUserId(userId)
    .checkpoint("查询用户订单")   // 出错时显示："查询用户订单 失败"
    .flatMap(order -> orderValidator.validate(order))
    .checkpoint("验证订单")       // 出错时显示："验证订单 失败"
    .subscribe();

第五类：时间相关（Time-based）

1. delayElements() —— 延迟发出每个元素

// delayElements：每个元素发射时延迟一定时间（异步，不阻塞主线程）
Flux.just("A", "B", "C")
    .delayElements(Duration.ofMillis(500))  // 每隔 500ms 发出一个
    .subscribe(System.out::println);
// A → 等500ms → B → 等500ms → C（主线程继续执行，不阻塞）

2. interval() —— 定时生成

// interval：定时器，每隔一定时间产生一个递增数字（无限流，需要手动取消）
Flux.interval(Duration.ofSeconds(1))  // 每秒产生一个数字，从 0 开始递增
    .subscribe(System.out::println);  // 0, 1, 2, 3...（无限输出）

3. timeout() —— 超时控制

// timeout：指定时间内没收到值就抛出 TimeoutException
userRepository.findById(1L)
    .timeout(Duration.ofSeconds(3))  // 3 秒内没返回就超时
    .subscribe(System.out::println);

第六类：触发执行（Subscribing）

创建和转换只是定义管道，不调用这些方法数据不会流动。

1. subscribe() —— 订阅并触发执行

// subscribe(onNext, onError, onComplete)：三个回调分别处理值、错误、完成
Flux.just("A", "B", "C")
    .subscribe(
        value -> System.out.println("收到: " + value),  // onNext：收到每个元素
        error -> System.err.println("错误: " + error),   // onError：出错的回调
        () -> System.out.println("完成")                  // onComplete：流正常结束时
    );

最简形式（只关心值）：

// 省略后两个参数，只处理正常情况
Flux.just("A", "B", "C").subscribe(value -> System.out.println(value));

2. block() —— 同步阻塞等待结果

// blockLast()：阻塞等待最后一个元素（用于测试，禁止在生产环境使用）
String result = Flux.just("A", "B", "C").blockLast();

// collectList() + block()：收集成 List 后阻塞获取
List<String> list = Flux.just("A", "B", "C").collectList().block();

// ⚠️ 警告：WebFlux 中禁止用 block()！会破坏响应式模型
//       EventLoop 线程被阻塞会导致整个网关卡死

3. toFuture() / toIterable() —— 转成传统类型

// toFuture：将 Mono 转成 Future（用于对接老代码）
Future<String> future = Flux.just("hello").next().toFuture();

// toIterable：将 Flux 转成交换迭代器（每次只取一个）
Iterable<String> iterable = Flux.just("A", "B", "C").toIterable();

三、完整案例

场景：查询用户信息，如果失败则降级，并发查其订单列表

public Mono<UserDetailVO> getUserDetail(Long userId) {
    // 第一路：查询用户信息（可能失败，降级）
    Mono<User> userMono = webClient.get()
        .uri("/users/{id}", userId)
        .retrieve().bodyToMono(User.class)
        .onErrorResume(e -> Mono.just(User.DEFAULT_USER))
        .checkpoint("查询用户信息");

    // 第二路：查询并过滤订单（并发，不阻塞第一路）
    Flux<Order> ordersFlux = Flux.fromIterable(orderRepository.findByUserId(userId))
        .filter(order -> !order.isCancelled())
        .map(Order::getSummary)
        .collectList()
        .flatMapMany(Flux::fromIterable)
        .checkpoint("过滤并转换订单");

    // 合并两路结果，超时控制，退避重试
    return Mono.zip(userMono, ordersFlux.collectList(), UserDetailVO::new)
        .map(vo -> {
            vo.setOrdersCount(vo.getOrders().size());
            return vo;
        })
        .timeout(Duration.ofSeconds(2))
        .onErrorResume(e -> Mono.just(UserDetailVO.EMPTY))
        .retryWhen(Retry.backoff(2, Duration.ofMillis(200)))
        .doOnSuccess(vo -> logger.info("用户 {} 查询完成, 订单数: {}",
            userId, vo.getOrdersCount()));
}

整个链路全部是异步非阻塞的，一条线程可以同时处理很多请求。

五、传统方法如何改成 Flux/Mono（实战改造）

原始同步代码（以查询用户名为例）：

@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public String getUserName(Long userId) {
        User user = userRepository.findById(userId);  // 同步，阻塞等数据库
        return user.getName();
    }
}

改造的目标是让 userRepository.findById() 返回 Mono<User>，从而让整条链路变成非阻塞。

方式一：Spring Data R2DBC（推荐，正式项目用）

Spring 官方出的响应式数据库访问方案，替代传统 JDBC，底层原生异步。

1. 引入依赖：

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-r2dbc</artifactId>
</dependency>
<dependency>
    <groupId>io.asyncer</groupId>
    <artifactId>r2dbc-mysql</artifactId>
</dependency>

2. Repository 改成响应式声明：

// 继承 ReactiveCrudRepository，框架自动生成返回 Mono/Flux 的实现
// 泛型参数：<实体类型, 主键类型>
public interface UserRepository extends ReactiveCrudRepository<User, Long> {
    // Flux：返回多个结果（查询列表）
    Flux<User> findByAgeGreaterThan(int age);

    // Mono：返回单个结果（查询单个）
    Mono<User> findByUsername(String username);
}

// findById(id) 直接继承自父接口，已返回 Mono<User>，无需额外定义

3. Entity 定义：

// @Table 指定数据库表名，@Id 指定主键字段
@Table("t_user")
@Data
public class User {
    @Id
    private Long id;
    private String username;
    private Integer age;
}

4. 配置文件（R2DBC 连接池）：

spring:
  r2dbc:
    url: r2dbc:mysql://localhost:3306/mydb  # R2DBC 连接 URL（不同于 JDBC）
    username: root
    password: 123456
    pool:
      initial-size: 5   # 初始连接数：启动时创建 5 个连接
      max-size: 20       # 最大连接数：连接池上限

关键：Repository 接口声明改成 Mono<User>，框架生成响应式实现，不需要手动写一行代码。

方式二：Mono.fromCallable() 包装（快速兼容现有代码）

不想改动整个数据库层时的桥接适配，本质是线程池模拟异步。

原始同步 Repository（不能改的业务代码）：

public class JdbcUserRepository {
    public User findById(Long id) {
        return jdbcTemplate.queryForObject(
            "SELECT * FROM t_user WHERE id = ?", userRowMapper, id
        );  // 同步阻塞
    }
}

包装成响应式：

@Repository
public class ReactiveUserRepository {

    private final JdbcUserRepository jdbcUserRepository;

    // fromCallable：把同步阻塞的 Callable 包装成 Mono
    // 关键：用 subscribeOn 把阻塞调用移到专用线程池，不占用 EventLoop
    public Mono<User> findById(Long id) {
        return Mono.fromCallable(() ->
            jdbcUserRepository.findById(id)  // 这里执行的是同步 JDBC 查询（阻塞）
        )
        // boundedElastic：专门为阻塞代码设计的线程池，有上限（默认 CPU 核数 × 10）
        .subscribeOn(Schedulers.boundedElastic());
    }
}

为什么要 subscribeOn(Schedulers.boundedElastic())？

灾难场景（不放 subscribeOn）：
  EventLoop 线程 → 执行同步 JDBC → 线程卡住等待数据库
                → 无法处理其他请求 → 网关卡死

正确场景（加上 subscribeOn）：
  EventLoop 线程 → 把任务扔给 boundedElastic 线程池 → 立即返回去处理其他请求
                ← JDBC 在后台线程完成 ← 回调通知 EventLoop 结果

boundedElastic 是专为"把阻塞代码适配成响应式"设计的线程池：
  - 有上限（不会无限创建线程耗尽内存）
  - 适合 I/O 阻塞（数据库、HTTP）操作
  ⚠️ 永远不要用 Schedulers.elastic()（已废弃，无上限，会导致内存泄漏）

Step 3：Service 层（响应式事务）

@Service
@Slf4j
public class UserService {

    @Autowired
    private UserRepository userRepository;
    @Autowired
    private PointsRepository pointsRepository;
    // R2DBC 事务管理器（类似 JDBC 的 TransactionTemplate）
    @Autowired
    private TransactionalOperator txOperator;

    // 注册用户（响应式事务：两个 INSERT 要么同时成功，要么同时回滚）
    public Mono<User> registerUser(String username, String email, int age) {
        // 1. 检查用户名是否已存在（非阻塞查询）
        return userRepository.findByUsername(username)
            .hasElement()  // 返回 Mono<Boolean>：true=已存在
            .flatMap(exists -> {
                if (exists) {
                    // 用户名冲突，返回错误 Mono
                    return Mono.error(new RuntimeException("用户名已存在"));
                }

                // 2. 构造用户实体
                User user = new User();
                user.setUsername(username);
                user.setEmail(email);
                user.setAge(age);
                user.setCreatedAt(LocalDateTime.now());

                // 3. 使用事务操作符包裹两个 INSERT
                // transactional() 让整个 lambda 在同一个数据库连接中执行
                return txOperator.transactional(
                    userRepository.save(user)          // 插入用户
                        .flatMap(savedUser -> {
                            // 4. 同时插入积分记录（初始积分 100）
                            UserPoints points = new UserPoints();
                            points.setUserId(savedUser.getId());
                            points.setPoints(100);
                            points.setUpdatedAt(LocalDateTime.now());
                            return pointsRepository.save(points)
                                .thenReturn(savedUser);  // 返回 User，忽略 Points 结果
                        })
                );
            })
            // 统一错误处理：数据库异常、用户名冲突都返回友好提示
            .onErrorResume(ex -> {
                log.error("注册失败: {}", ex.getMessage());
                return Mono.error(new BizException("注册失败，请稍后重试"));
            });
    }

    // 查询用户列表（分页，响应式）
    public Flux<User> getUsersByAge(int minAge, int page, int size) {
        return userRepository.findByAgeGreaterThan(minAge)
            .skip(page * (long) size)
            .take(size);
    }
}

    public Mono<ServerResponse> register(ServerRequest request) {

                );
            });

}

响应式事务原理（TransactionalOperator 如何工作）：

txOperator.transactional(Mono<T> mono) 执行流程：

1. 从连接池获取一个 Connection（异步，不阻塞线程）
2. 设置 Connection 为手动提交模式（autocommit=false）
3. 在这个 Connection 上执行 mono 中的所有数据库操作
4. mono 完成时：
   ├─ 成功 → COMMIT，释放连接回池
   └─ 异常 → ROLLBACK，释放连接回池

关键：整个事务过程中，线程不会被阻塞
     等待数据库 I/O 时，EventLoop 线程去处理其他请求

连接池配置（生产环境）

spring:
  r2dbc:
    url: r2dbc:mysql://192.168.1.50:3306/user_db?sslMode=DISABLED
    username: root
    password: root123
    pool:
      initial-size: 5       # 启动时创建 5 个连接
      max-size: 20         # 最大 20 个连接（比 JDBC 少，因为是非阻塞，一个连接可处理大量请求）
      max-idle-time: 30m   # 空闲 30 分钟后回收
      acquire-retry:
        max-attempts: 3    # 获取连接失败最多重试 3 次
        delay: 100ms       # 重试间隔 100ms

维度 JDBC（同步） R2DBC（响应式）

数据库连接数 100 并发 = 100 连接 100 并发 = 10-20 连接

适用场景 简单 CRUD 高并发 I/O 密集型

改成 WebClient（原生的异步非阻塞）：

// WebClient 是 Spring 的响应式 HTTP 客户端，原生异步非阻塞
public Mono<String> getUserName(Long userId) {
    return webClient.get()
        .uri("http://user-service/api/user/{id}", userId)  // 构建请求 URI
        .retrieve()                                        // 发送 HTTP 请求并获取响应
        .bodyToMono(UserDTO.class)                         // 把响应体解析成 Mono<UserDTO>
        .map(UserDTO::getName)                            // 转成 Mono<String>（用户名）
        .timeout(Duration.ofSeconds(3));                   // 3 秒超时控制
}

// 各步骤说明：
// 1. get()：指定 HTTP 方法（GET）
// 2. uri()：指定请求地址，支持路径参数替换
// 3. retrieve()：发起请求，获取响应对象
// 4. bodyToMono(UserDTO.class)：将响应体 JSON 反序列化为对象（异步）
// 5. map()：提取用户名字段，类型从 Mono<UserDTO> 转为 Mono<String>
// 6. timeout()：3 秒内没返回则抛出 TimeoutException

// retrieve() vs exchangeToMono()：
// retrieve()：自动处理 HTTP 状态码，4xx/5xx 会抛异常（简单场景）
// exchangeToMono()：可访问完整响应信息，包括 Header、状态码（复杂场景）

3.3 如何在 Gateway 中实现限流？

答案： 使用 Redis + 令牌桶算法：

限流算法：

  • 计数器固定窗口算法
  • 计数器滑动窗口算法
  • 漏桶算法
  • 令牌桶算法（推荐，应对突发流量）

【技术原理扩展】

四种限流算法对比：

算法 特点 适用场景
计数器固定窗口 简单，但临界时刻有 2 倍流量 简单限流
滑动窗口 平滑，无临界突变 精确限流
漏桶 严格匀速，突发流量被平滑 流量整形
令牌桶（推荐） 允许突发，最大 = 桶容量 应对突发流量

令牌桶 vs 漏桶区别：

  • 漏桶：请求匀速输出，突发时多余请求被拒绝
  • 令牌桶：令牌匀速补充，突发时可用桶中令牌（最大突发量 = 桶容量）

Redis + Lua 实现令牌桶：

local key = KEYS[1]        -- 限流 key
local rate = tonumber(ARGV[1])      -- 每秒补充令牌数
local capacity = tonumber(ARGV[2])  -- 桶容量

local now = redis.call('TIME')[1]
local last = redis.call('HGET', key, 'last') or now
local tokens = tonumber(redis.call('HGET', key, 'tokens')) or capacity

-- 计算需要补充的令牌数
local elapsed = math.max(0, now - last)
local add_tokens = elapsed * rate / 1000
tokens = math.min(capacity, tokens + add_tokens)

-- 尝试获取令牌
if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HSET', key, 'tokens', tokens)
    redis.call('HSET', key, 'last', now)
    return 1  -- 通过
else
    return 0  -- 拒绝
end

Key 解析器示例：

        exchange.getRequest().getHeaders().getFirst("X-User-Id")

}

// 按 IP 限流
@Bean

    return exchange -> Mono.just(
        exchange.getRequest().getRemoteAddress().getAddress().getHostAddress()
    );
}

4.1 什么是服务雪崩？如何避免？

答案： 服务雪崩：因某个服务故障，导致级联故障，整个系统不可用。

原因链条：

服务响应慢 → 请求堆积 → 线程池满 → 级联失败 → 整个系统崩溃

避免方案：

  • 熔断：Sentinel/Resilience4j，失败率高时快速失败
  • 限流：限制并发请求数
  • 超时控制：设置合理超时时间（如 3 秒）
  • 服务隔离：线程池/信号量隔离
  • 异步解耦：消息队列缓冲

【技术原理扩展】

服务雪崩的完整链条：

[0s] 服务 A 正常，响应时间 100ms
[1s] 服务 A 变慢（DB 慢查询），响应时间 5000ms
[2s] 服务 A 线程池耗尽（100 个线程全部阻塞）
[3s] 调用服务 A 的服务 B 也开始超时
[4s] 级联效应，服务 C、D、E... 全部崩溃
[5s] 整个系统不可用

雪崩原因分类：

原因 场景 解决方案
硬件故障 服务器宕机、机房断电 多机房部署、自动 failover

流量激增 促销、秒杀、爬虫 限流、扩容
依赖服务故障 第三方 API 不可用 熔断、降级、隔离

4.2 熔断和降级的区别？

答案：

  • 熔断（Circuit Breaker）：类似保险丝，当错误率达到阈值时"熔断"不再调用后端，避免级联故障
  • 降级（Fallback）：熔断后或服务不可用时，返回降级数据（如缓存、默认值），保证系统部分可用

【技术原理扩展】

熔断器模式原理（状态机转换）：

                    │
         失败率      ▼
    ───────────────────────►
    │                            │
    ▼                            │
┌────────┐  失败率超阈值   ┌────────┐  尝试放行  ┌────────┐
│ Closed │ ────────────► │  Open  │ ─────────► │ Half   │
│ 关闭   │                │ 开启   │            │ Open   │
│ 正常   │                │ 熔断中 │            │ 半开   │
│ 调用   │                │ 直接   │            │ 有限   │
└────────┘                │ 返回   │            │ 放行   │
    ▲                     └────────┘            └────────┘
    │                         │                    │
    │                         │                    │
    │  连续成功              成功                 失败
    │  重置计数器             进入 Closed          回到 Open
    └───────────────────────────────────────────────┘

降级场景分类：

场景 降级策略 示例

4.3 Sentinel 服务熔断过程？

答案： 服务熔断一般有三种状态：

  1. 熔断关闭状态（Closed）：服务没有故障时，熔断器所处的状态，对调用方的调用不做任何限制

  2. 熔断开启状态（Open）：后续对该服务接口的调用不再经过网络，直接执行本地的 fallback 方法

  3. 半开状态（Half-Open）：尝试恢复服务调用，允许有限的流量调用该服务，并监控调用成功率。如果成功率达到预期，则说明服务已恢复，进入熔断关闭状态；如果成功率仍旧很低，则重新进入熔断关闭状态

Sentinel 滑动窗口算法：

滑动窗口结构（10个Bucket，每窗口1秒）：
┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐

计算：最近10秒异常比例 = (4+3+2+5+8) / (10+8+5+9+10) ≈ 52%
如果阈值是 50%，则触发熔断

【实战案例】@SentinelResource 熔断降级实战

场景： 订单服务（order-service）调用库存服务（stock-service），库存服务频繁超时/报错，需要用 Sentinel 保护。

用户下单 → 订单服务调用库存服务 → 库存服务故障 → 熔断 → 返回降级结果
                                              ↓
                                    用户看到"库存校验中，请稍后"

Step 1：引入依赖

<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-core</artifactId>
    <version>1.8.1</version>
</dependency>

Step 2：业务代码——用 @SentinelResource 标注被保护的方法

@Service
public class OrderService {

    @Autowired
    private RestTemplate restTemplate;

    // 关键：@SentinelResource 标注对外调用的方法
    // value = "checkStock" 是资源名，Sentinel Dashboard 中按这个名字配置规则
    // blockHandler = "checkStockBlock" 是触发限流/熔断时的降级方法
    // fallback = "checkStockFallback" 是业务异常时的降级方法
    @SentinelResource(
        value = "checkStock",              // 资源名（必填）
        blockHandler = "checkStockBlock",   // 触发熔断/限流时执行此方法
        fallback = "checkStockFallback"    // 业务抛异常时执行此方法
    )
    public OrderResult createOrder(Long productId, Integer quantity) {
        // 调用库存服务（假设 stock-service 经常超时或报错）
        String response = restTemplate.getForObject(
            "http://stock-service/api/stock/check?productId=" + productId,
            String.class
        );
        // 正常流程：库存充足，下单成功
        return new OrderResult(true, "下单成功");
    }

    // ===== 降级方法必须 static，返回值和参数必须与原方法一致 =====

    // 降级方法1：触发限流/熔断时（block）调用这个
    public static OrderResult checkStockBlock(Long productId, Integer quantity,
            BlockException e) {
        // 限流/熔断时走这里
        return new OrderResult(false, "系统繁忙，请稍后重试");
    }

    // 降级方法2：业务代码抛异常时调用这个
    public static OrderResult checkStockFallback(Long productId, Integer quantity,
            Throwable t) {
        // 记录日志，方便排查
        log.error("库存服务调用失败, productId={}, error={}", productId, t.getMessage());
        // 返回降级结果：给用户一个友好提示，同时记录订单待处理
        return new OrderResult(false, "库存校验超时，已记录订单");
    }
}

Step 3：Sentinel 配置——定义熔断规则（代码或 Dashboard）

// 方式1：代码中配置熔断规则（应用启动时加载）
@Configuration
public class SentinelConfig {

    @PostConstruct
    public void initDegradeRule() {
        List<DegradeRule> rules = new ArrayList<>();
        DegradeRule rule = new DegradeRule("checkStock")  // 对应 @SentinelResource 的 value
            .setGrade(CircuitBreakerStrategy.ERROR_RATE.getType()) // 按异常比例熔断
            .setCount(0.5)          // 50% 异常率触发熔断
            .setMinRequestAmount(5)   // 窗口内至少 5 个请求才统计（避免冷启动误判）
            .setStatIntervalMs(10000)  // 10 秒统计窗口
            .setTimeWindow(10);        // 熔断持续 10 秒
        rules.add(rule);
        DegradeRuleManager.loadRules(rules);
    }
}

// 方式2：Sentinel Dashboard 动态配置（生产环境推荐）
// 登录 Dashboard → 流控规则 → 新增规则
// 资源名：checkStock
// 阈值类型：异常比例
// 阈值：0.5（50%）
// 熔断时长：10 秒

熔断触发后的时序：

正常状态（Closed）：
  请求 → checkStock() → stock-service 正常 → 返回结果 ✅

故障累计：
  10 秒内 5 个请求中，3 个超时/报错 → 异常率 60% > 50% 阈值 → 触发熔断

熔断开启（Open）：
  后续请求 → checkStockBlock() → 直接返回 "系统繁忙，请稍后重试" ❌
  不再调用 stock-service（保护它不被拖垮）

10 秒后半开（Half-Open）：
  允许 1 个请求通过 → 如果成功 → 熔断关闭，正常调用
                         如果失败 → 继续熔断 10 秒

为什么需要两个降级方法（blockHandler vs fallback）？

降级方法 触发条件 使用场景
blockHandler Sentinel 规则拦截（限流、熔断、系统保护） 保护系统不被压垮，返回友好提示
fallback 业务代码抛出异常（超时、网络错误） 记录日志 + 返回兜底数据，订单不丢失

流控策略详解：

策略 说明 适用场景
直接拒绝 QPS 超出阈值，直接拒绝 保护系统不被压垮
Warm Up 冷启动，逐步增加阈值 秒杀开始，缓慢加热
排队等待 匀速排队，超时放弃 削峰填谷，延迟敏感

K8s Client 使用示例：

// Kubernetes Client 使用示例
import io.kubernetes.client.openapi.apis.CoreV1Api;

public class K8sTaskScheduler {

    private CoreV1Api api;

    public void createTaskPod(TaskConfig task) throws ApiException {
        // 1. 创建 Pod 配置（使用 Builder 模式链式构建）
        V1Pod pod = new V1PodBuilder()
            .withNewMetadata()
                .withName("task-" + task.getId())   // Pod 名称（K8s 中唯一）
                .addToLabels("app", "data-task")    // 添加标签，用于 Service 筛选
            .endMetadata()
            .withNewSpec()
                .addNewContainer()
                    .withName("task")              // 容器名称（Pod 内唯一）
                    .withImage(task.getImage())    // 容器镜像地址
                    // 设置资源限制：CPU 500m=0.5核，内存 512Mi=512MB
                    .withResources(new V1ResourceRequirements()
                        .addToLimits("cpu", new Quantity("500m"))
                        .addToLimits("memory", new Quantity("512Mi")))
                .endContainer()
            .endSpec()
            .build();

        // 2. 提交到 K8s 集群
        // 参数：命名空间、Pod 对象、是否立即返回、是否宽松容错、超时时间
        api.createNamespacedPod("default", pod, "true", null, null);
    }
}

// 说明：
// - V1PodBuilder：链式 API，替代传统 JavaBean 的 setter
// - withNewMetadata / endMetadata：成对使用，定义元数据块
// - createNamespacedPod：创建有命名空间的 Pod（vs createPod 创建集群级 Pod）
// - "true" 参数：是否立即返回（false=等待 Pod 调度完成）

6.8 Pod 的健康检查机制？

答案： Kubernetes 通过三类探针来监测 Pod 健康：

  • livenessProbe（存活探针）：检测容器是否正常运行，不健康时会重启容器
  • readinessProbe（就绪探针）：判断容器是否可以接收流量，不健康时 Pod 会被移出 Service
  • startupProbe（启动探针）：用于避免业务启动缓慢导致的探针失败

【技术原理扩展】

三类探针详解：

探针 作用 失败后果 应用场景
livenessProbe 容器是否存活 重启容器 检测死锁、无限循环
readinessProbe 是否可以接收流量 从 Service 移出 初始化、加载中
startupProbe 容器是否启动完成 延迟其他探针 慢启动应用

探针配置示例：

spec:
  containers:
  - name: order-service
    livenessProbe:
      httpGet:
        path: /health/liveness
        port: 8080
      initialDelaySeconds: 30   # 启动30秒后开始探测
      periodSeconds: 10         # 每10秒探测一次
      failureThreshold: 3        # 连续3次失败则重启

    readinessProbe:
      httpGet:
        path: /health/readiness
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5

    startupProbe:
      httpGet:
        path: /health/startup
        port: 8080
      failureThreshold: 30      # 30次失败（30*10s=5分钟超时）
      periodSeconds: 10

6.9 Pod 创建过程？

答案：

  1. 用户通过 kubectl 或 API 客户端提交需要创建的 Pod 信息给 API Server
  2. API Server 验证用户权限信息，生成 Pod 对象信息并存入 etcd，然后返回确认信息给客户端
  3. API Server 将 etcd 中的 Pod 对象变化反馈给其他组件
  4. 调度器 Scheduler 发现有新的 Pod 对象，调用算法为 Pod 分配最佳主机
  5. kubelet 通过 watch 机制跟踪到分配给本节点的 Pod，调用容器运行时启动容器

NodeAction 实现示例：

@Component
public class IntentRecognitionNode implements NodeAction {

    private final LlmService llmService;

    @Override
    // apply：节点执行入口，接收全局状态，返回新状态（Map）
    // 状态（State）贯穿整个工作流，每个节点读写其中的数据
    public Map<String, Object> apply(OverAllState state) throws Exception {
        // 1. 从全局状态读取输入（上一节点产出的数据）
        String userInput = StateUtil.getStringValue(state, INPUT_KEY);

        // 2. 调用 LLM 服务（流式返回）
        Flux<ChatResponse> responseFlux = llmService.callUser(prompt);

        // 3. 创建流式生成器（将 LLM 响应封装成 Graph 的流式输出格式）
        //    this.getClass()：标识当前节点，用于追踪
        //    state：传递上下文给下游节点
        //    "正在进行意图识别..."：开始时输出的提示
        //    "\n意图识别完成！"：完成后输出的提示
        //    parseResult：流式片段到达时执行的转换函数
        Flux<GraphResponse<StreamingOutput>> generator = FluxUtil
            .createStreamingGeneratorWithMessages(
                this.getClass(), state,
                "正在进行意图识别...",
                "\n意图识别完成！",
                result -> Map.of(INTENT_OUTPUT, parseResult(result)),  // 转换结果存入状态
                responseFlux);

        // 4. 返回新状态（output 字段存流式生成器，供下游节点消费）
        return Map.of(INTENT_RECOGNITION_NODE_OUTPUT, generator);
    }
}

10.2 如何做 SQL 性能分析？

答案：

10.5 索引失效的常见场景？

答案：

  1. 违反最左前缀：联合索引未按顺序查询
  2. 索引列运算：where id+1=100
  3. 索引列函数：where substring(name,1,2)='张'
  4. 类型隐式转换：字符串不加引号 where phone=13800138000
  5. 模糊查询前置 %：where name like '%张'
  6. or 连接非索引列：where id=1 or age=20（age 无索引）
  7. != / not in / not exists：大概率失效
  8. 数据分布不均：全表扫描比索引更快

【技术原理扩展】

索引失效原理详解：

联合索引 (name, age, gender) 存储结构：

        B+ Tree
           │
    ┌───────┴───────┐
    │   索引节点    │
    └───────┬───────┘
            │
    ┌───────┴───────┐
    │   叶子节点    │
    │ [name1,age1] → [行指针]
    │ [name2,age2] → [行指针]
    └───────────────┘

使用情况分析：

✓ WHERE name = '张三'            # 使用索引（最左前缀）
✓ WHERE name = '张三' AND age = 20   # 使用索引
✓ WHERE name = '张三' AND age > 20   # 使用索引
✗ WHERE age = 20                   # 不使用（跳过 name）
✗ WHERE age = 20 AND gender = 'M'  # 不使用（中间断开）

常见索引失效案例：

-- 案例1：函数导致索引失效
-- 索引: idx_create_time (create_time)
SELECT * FROM orders WHERE YEAR(create_time) = 2024;
-- 修复：改写为范围查询
SELECT * FROM orders WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';

-- 案例2：隐式类型转换
-- phone 字段是 VARCHAR，查询用数字
SELECT * FROM users WHERE phone = 13800138000;
-- 修复：加引号
SELECT * FROM users WHERE phone = '13800138000';

-- 案例3：OR 导致索引失效
-- id 有索引，status 无索引
SELECT * FROM orders WHERE id = 1 OR status = 'paid';
-- 修复：拆分为 UNION
SELECT * FROM orders WHERE id = 1
UNION
SELECT * FROM orders WHERE status = 'paid';

// 1. 权限控制模型：定义用户可访问的表、字段、行级过滤条件
public class SQLPermission {
    Set<String> allowedTables;      // 白名单：允许访问的表（如 user_orders）
    Set<String> allowedColumns;      // 字段权限：允许查询的字段（如排除 password）
    String rowFilterCondition;       // 行级过滤：如 "user_id = 123"，自动注入 WHERE 条件
}

// 2. SQL 改写沙箱：执行前清理危险关键字，注入权限条件
public class SQLSanitizer {
    public String sanitize(String sql, SQLPermission permission) {
        // 移除危险关键字：防止 DROP TABLE、TRUNCATE 等破坏性操作
        sql = sql.replaceAll("(?i)\\bDROP\\b", "");    // (?i) 不区分大小写
        sql = sql.replaceAll("(?i)\\bTRUNCATE\\b", "");
        sql = sql.replaceAll("(?i)\\bDELETE\\b(?!\\s+FROM)", ""); // 保留 DELETE FROM

        // 注入行级权限条件：用户在查询末尾自动加上 user_id 限制
        // 例如：SELECT * FROM orders → SELECT * FROM orders WHERE user_id = 123
        sql = sql + " WHERE " + permission.getRowFilterCondition();
        return sql;
    }
}

十二、分布式事务

10.1 什么是分布式事务？

答案： 跨多个数据库/服务的事务操作，保证要么全部成功，要么全部失败。

典型场景： 订单服务扣减库存 → 库存服务扣减 → 账户服务扣款，任何一步失败都要全部回滚。

12.2 2PC 和 3PC 的流程和优缺点？

答案：

2PC（两阶段提交）：

  1. 事务协调器询问各个参与者是否可以正常执行
  2. 如果都可以，则发送 commit；如果有问题，发送 rollback

优点：尽量保证数据强一致，实现成本较低 缺点：

  • 单点问题：事务协调器宕机会导致资源阻塞
  • 同步阻塞：资源管理器一直处于阻塞
  • 数据不一致：可能只有部分参与者收到 commit 通知

3PC（三阶段提交）： 在 2PC 的第一阶段和第二阶段中插入一个准备阶段，引入超时机制。

优点：解决了事务协调器宕机导致的阻塞问题 缺点：多了一次网络通信，性能更差，数据不一致问题依然存在

12.3 Seata 的三种事务模式？

答案：

模式 说明 适用场景
AT 模式 基于 undo/redo 日志，自动回滚 简单 CRUD，侵入性低

Seata 四种事务模式对比：

Saga 正向补偿（无需回滚） 中 高 长事务、工作流

│ 2. 注册分支事务（将本地事务注册到全局事务）                  │

┌─────────────────────────────────────────────────────────────┐
│ - 提交：异步删除 undolog                                    │

└─────────────────────────────────────────────────────────────┘

10.4 Seata AT 模式的两阶段过程？

答案： 一阶段：开启全局事务、注册分支事务、储存全局锁、业务数据和回滚日志（undoLog）进行提交

二阶段：事务协调者根据所有分支的情况，决定本次全局事务是 Commit 还是 Rollback（二阶段是完全异步删除 undolog 日志，全局事务、分支事务、储存的全局锁）

【技术原理扩展】

AT 模式 undolog 原理：

回滚流程：

    // 2. 逆向补偿

}

  • 全局锁保证：同一行数据在同一全局事务内只能被一个分支操作
  • 本地锁释放时机：一阶段就释放本地锁，二阶段异步处理

Seata AT 模式两阶段执行流程（以扣减余额为例）：

【一阶段：执行阶段】
  1. 开启本地事务
  2. 执行 UPDATE account SET balance = balance - 100 WHERE id = 1
  3. Seata 自动拦截，插入 undo_log：
     beforeImage: {balance: 1000}
     afterImage:  {balance: 900}
  4. 提交本地事务（本地锁在一阶段就释放了，性能高）
  5. 向 TC（事务协调者）注册分支，报告执行结果

【二阶段：完成阶段】
  ├─ TC 收到所有分支报告（全成功）
  │   → 发送 Commit 指令
  │   → 所有服务异步删除 undo_log ✅
  │
  └─ TC 收到任意分支失败报告
      → 发送 Rollback 指令
      → 各服务逆序执行 undo_log：
          UPDATE account SET balance = 1000 WHERE id = 1  （还原）
          DELETE FROM undo_log WHERE xid = 'xxx'
      → 数据完全回滚 ✅

为什么 AT 模式能"自动"回滚？ Seata 通过 DataSourceProxy 代理数据源，在 SQL 执行前后自动记录前后镜像（beforeImage/afterImage），写入 undo_log 表。回滚时逆向执行即可，无需业务代码介入。

AT vs TCC 选型建议：

维度 AT 模式 TCC 模式
侵入性 低（只需加注解） 高（需写 Try/Confirm/Cancel 三个方法）
性能 高（一阶段就释放锁） 中（Try 阶段锁定资源）
回滚粒度 基于 SQL（整行） 基于业务（字段级别）
适用场景 简单 CRUD（增删改） 特殊场景（如冻结部分金额）
失败率 低（Seata 自动处理） 中（Confirm/Cancel 需业务保证幂等）

注意： 全局事务不要包太大（控制在 3-5 个服务以内），全局锁持有时间越长并发越低。

10.5 TCC 模式如何保证幂等性？

答案：

  1. 业务幂等：数据库唯一约束（如订单 ID）
  2. 状态检查：每次操作前检查状态，已处理则跳过
  3. 幂等 Token：生成唯一 Token，防止重复提交

【技术原理扩展】

TCC 三阶段详解：

┌─────────────────────────────────────────────────────────────┐
│                         Try 阶段                            │
│  预留资源：冻结金额、预扣库存、预创建订单                     │
│  检查业务可行性：库存是否充足、余额是否足够                   │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                      Confirm 阶段                            │
│  确认执行：真正扣款、真正减库存、真正创建订单                 │
│  如果 Try 阶段成功，执行 Confirm                             │
│  幂等保证：幂等 Token 防止重复执行                            │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                      Cancel 阶段                             │
│  取消预留：释放冻结金额、返还库存、删除订单                   │
│  如果 Try 阶段失败或超时，执行 Cancel                         │
│  幂等保证：状态检查，已取消则跳过                            │
└─────────────────────────────────────────────────────────────┘

幂等实现示例：

public class TCCService {

    // 幂等 Token 存储
    private Map<String, TCCState> tccStateCache;

    public boolean tryPhase(String txId, int amount) {
        // 检查幂等
        if (tccStateCache.containsKey(txId)) {
            return tccStateCache.get(txId) == TCCState.TRY_SUCCESS;
        }
        // 预留资源
        accountService.freeze(txId, amount);
        tccStateCache.put(txId, TCCState.TRY_SUCCESS);
        return true;
    }

    public boolean confirmPhase(String txId) {
        TCCState state = tccStateCache.get(txId);
        if (state == TCCState.CONFIRMED) {
            return true;  // 幂等：已确认，跳过
        }
        accountService.deduct(txId);
        tccStateCache.put(txId, TCCState.CONFIRMED);
        return true;
    }

    public boolean cancelPhase(String txId) {
        TCCState state = tccStateCache.get(txId);
        if (state == TCCState.CANCELLED) {
            return true;  // 幂等：已取消，跳过
        }
        accountService.unfreeze(txId);
        tccStateCache.put(txId, TCCState.CANCELLED);
        return true;
    }
}

十三、Redis 缓存

11.1 Redis 雪崩、击穿、穿透？

答案：

雪崩：大量缓存数据在同一时间过期，导致大量请求直接打到数据库 解决方案：设置随机过期时间、使用多级缓存、加锁

击穿：一个热点 key 过期瞬间，大量请求直接打到数据库 解决方案：使用互斥锁、永不过期策略

穿透：查询不存在的数据，绕过缓存直接打到数据库 解决方案：布隆过滤器、缓存空值、参数校验

【技术原理扩展】

Redis 三高问题详解：

问题 原因 现象 解决方案
雪崩 大量 key 同时过期 大量请求打到 DB 随机过期时间、多级缓存、加锁
击穿 热点 key 过期瞬间 单点并发打到 DB 互斥锁、永不过期 + 逻辑过期
穿透 查询不存在数据 请求绕过缓存打到 DB 布隆过滤器、缓存空值、参数校验

布隆过滤器原理：

┌────────────────────────────────────────────────────────────────┐
│                    Bloom Filter 原理                           │
│                                                                 │
│  数据结构：Bit Array（位数组）                                  │
│                                                                 │
│  插入 "user:100"：                                              │
│  1. 计算哈希：h1("user:100") = 3, h2("user:100") = 7           │
│  2. 设置位：array[3] = 1, array[7] = 1                          │
│                                                                 │
│  查询 "user:100" 是否存在：                                     │
│  1. 计算哈希：h1, h2                                            │
│  2. 检查位：array[3] 和 array[7] 是否都为 1                    │
│  3. 任一为 0 → 不存在                                           │
│  4. 都为 1 → 可能存在（可能有误判）                             │
│                                                                 │
│  特点：                                                         │
│  - 空间效率高（1% 误判率下，每个元素约 10 bits）                │
│  - 不存储实际数据                                               │
│  - 不支持删除（可使用 Counter Bloom Filter）                    │
└────────────────────────────────────────────────────────────────┘

Redis 布隆过滤器使用：

互斥锁实现（防止击穿）：

public String getFromCache(String key) {
    // 1. 先查缓存
    String value = redis.get(key);
    if (value != null) {
        return value;
    }

    // 2. 互斥锁，防止击穿
    String lockKey = "lock:" + key;
    String token = UUID.randomUUID().toString();

    if (redis.setnx(lockKey, token, 30)) {  // 30秒过期
        try {
            // 3. 查数据库
            value = db.get(key);
            // 4. 写入缓存
            redis.setex(key, 3600, value);
            return value;
        } finally {
            // 5. 释放锁
            if (token.equals(redis.get(lockKey))) {
                redis.del(lockKey);
            }
        }
    } else {
        // 其他线程正在加载，等待后重试
        Thread.sleep(50);
        return getFromCache(key);
    }
}

11.2 Redis 和数据库保证数据一致性？

答案：

  1. 延迟双删：先删缓存，再更新数据库，再删缓存
  2. 更新缓存：更新数据库后，异步更新缓存
  3. 分布式锁：使用 Redisson 分布式锁

【技术原理扩展】

缓存一致性策略对比：

策略 原理 优点 缺点
延迟双删 删除缓存 → 更新 DB → 再删缓存 实现简单 有时间窗口不一致
异步更新 更新 DB → 异步更新缓存 性能好 可能失败
订阅 binlog 监听 DB 变更，异步更新缓存 实时性好 复杂度高
分布式锁 写入时加锁，保证串行 一致性好 性能差

延迟双删详解：

1. 删除缓存
   redis.del(key)

2. 更新数据库
   UPDATE orders SET status = 'paid' WHERE id = 1

3. 延迟删除缓存（异步）
   Thread.sleep(500ms)
   redis.del(key)

为什么需要延迟？
- 防止脏读：主从延迟导致读到旧数据
- 场景：线程 A 更新了 DB，还没来得及删除缓存时
        线程 B 读取了缓存（老数据），写入缓存
        延迟删除可以清除这个脏数据

订阅 binlog 方案（推荐）：

┌────────────┐      ┌────────────┐      ┌────────────┐
│    MySQL   │ ───> │ Canal      │ ───> │   MQ       │ ───> 更新缓存
│   binlog   │      │ 监听变更   │      │ 异步消息   │
└────────────┘      └────────────┘      └────────────┘

优点：
- 不侵入业务代码
- 实时性好
- 解耦数据库和缓存

十四、MySQL 高级

12.1 MySQL 索引分类？

答案：

  • 主键索引：PRIMARY KEY，非空唯一
  • 唯一索引：UNIQUE，值唯一，允许 NULL
  • 普通索引：INDEX，仅加速查询
  • 联合索引：多个字段组合建索引，遵循最左前缀原则
  • 覆盖索引：查询字段全部在索引中，无需回表

【技术原理扩展】

MySQL 索引结构（B+ Tree）：

B+ Tree 特点：
- 非叶子节点只存储索引，不存储数据
- 叶子节点存储所有数据（InnoDB）
- 叶子节点之间用双向链表连接（范围查询快）
- 高度一般 2-3 层，支持千万级数据

┌────────────────────────────────────────────────┐
│                     Root                        │
│              [page 1, page 2]                  │
└─────────────────┬──────────────────────────────┘
                  │                    │
        ┌─────────┴─────────┐   ┌─────┴─────┐

   (索引页)            (索引页)      (数据页)

联合索引最左前缀原则：

-- 创建联合索引
CREATE INDEX idx_name_age_gender ON users(name, age, gender);

-- 使用情况分析
✓ SELECT * FROM users WHERE name = '张三'        -- 使用（最左前缀）
✓ SELECT * FROM users WHERE name = '张三' AND age = 20  -- 使用
✓ SELECT * FROM users WHERE name = '张三' AND age > 20   -- 使用
✗ SELECT * FROM users WHERE age = 20               -- 不使用（跳过 name）
✗ SELECT * FROM users WHERE age = 20 AND gender = 'M'    -- 不使用（中间断开）

覆盖索引示例：

-- 覆盖索引：查询字段都在索引中，无需回表
CREATE INDEX idx_name_age ON users(name, age);

-- 执行计划：Using index（覆盖索引）
SELECT name, age FROM users WHERE name = '张三';

-- 需要回表：Using index condition（索引下推）
SELECT * FROM users WHERE name = '张三';
